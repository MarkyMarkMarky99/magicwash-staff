# WashQueue

WashQueue is a shared washing-machine basket queue for signed-in staff. A sender photographs a basket and may add a free-text instruction or washing programme. It is independent of orders and JobTickets. All machines share one FIFO queue, ordered by createdAt ascending. Only the first Pending basket has the Load action, and only operators get it; later Pending baskets cannot be loaded through the UI until they reach the front.

Every basket is weighed on the scale twice, and each weighing needs a photo of the basket on the scale as evidence. The sender enters the dry basket weight (`weightBeforeKg`) when booking; the operator enters the washed (wet) weight (`weightAfterKg`) when unloading. A booking starts Pending (Waiting). Loading changes Pending to In Progress (In machine), unloading changes In Progress to Completed (Ready for pickup), and collection changes Completed to Collected. Cancellation changes Pending, In Progress or Completed to Cancelled; earlier action stamps are kept. Each action stamps its corresponding timestamp and StaffId, plus updatedAt and updatedBy. Created and updated audit timestamps are produced by the existing repository audit configuration; action timestamps use formatBangkokTimestamp. All business timestamps use yyyy-MM-dd HH:mm:ss in Asia/Bangkok.

GET /api/wash-queue returns every Pending, In Progress and Completed basket, plus Collected and Cancelled baskets updated today in Bangkok. The result is an unpaginated array sorted by createdAt ascending in the standard success envelope. POST /api/wash-queue accepts photoUrl (a non-empty string, the booking photo taken on the scale), weightBeforeKg (required number) and optional instruction (string or null), and returns the created basket with HTTP 201. The server generates WQ- followed by generateShortId(), sets Pending and workMinutes null, and takes both audit actors from authenticated req.staff.staffId. Client-supplied identity, status and audit fields are rejected.

PATCH /api/wash-queue/:id accepts an `action`: load, collect or cancel alone, or unload together with `weightAfterKg` (number) and `unloadPhotoUrl` (the photo taken on the scale). It returns the updated basket. An unknown id returns 404; an action incompatible with the current status returns 409 and an explanatory message. The frontend displays that message and reloads the list. Reads normalize native Sheets/GViz datetime values to the canonical Bangkok format, and blank nullable write echoes to null.

Cancellation, loading, unloading and collection are gated in the frontend only (see the permission table); the server has no role, ownership or FIFO checks, by owner decision. An operator is an admin or staff whose Position, trimmed and compared case-insensitively, equals WashOperator; Position comes from the existing /api/staff/me service and sender names from the staff store. Cancellation asks for confirmation. Shared Sheets reads and writes do not provide atomic compare-and-set across operators, so the status check is a read-before-update check, not a transactional concurrency guarantee.

Rows also carry `weightBeforeKg`, `weightAfterKg`, `unloadPhotoUrl` and `machineId`, each nullable.

The page is one screen at `/wash-queue`, with no tabs, so every staff member sees the whole queue. It uses `ListPageLayout` with `GenericTabs` as the filters strip: All, Waiting, In machine and Ready, each with a count. The active tab lives in the `?tab=` query (`waiting`, `in-machine` or `ready`; All has no key) and changes with `router.replace`. All shows the sections from top to bottom as In machine, Waiting and a collapsible Ready for pickup, each hidden when empty; a filtered tab shows only its section, or one empty state when that list is empty. When the whole queue is empty one empty state shows. Each section header has a lime left bar, the title, a tiny uppercase subtitle and an uppercase basket counter. A hint line under the tabs ("Left: cancel", "Right: load / unload / pick up", limited to what the visible rows allow) is shown only when the user has at least one swipeable row. Rows are white cards with a weight column (the dry weight, or the washed weight on Ready rows, with "kg" under it), a thin divider, the sender with a "You" badge on the user's own baskets and a "Next" badge on the first waiting basket, an uppercase status line (IN MACHINE with the machine id when known, WAITING · #n, READY FOR PICKUP), a meta line (booking time as `today HH:mm` otherwise the Bangkok date and time, then the note; Ready rows start it with "Dry X kg") and a 56 px photo tile that opens the shared photo viewer. The tile carries a status dot (dashed Waiting, primary sync In machine, lime check Ready), and Ready rows also show a small tile for the unload photo. Booking is the bottom-right Photo button: the shared `WeightPrompt` ("Weigh the basket", explaining the photo must show the basket on the scale), then the shared CameraOverlay, then upload via uploadToStorage(file, 'wash-queue'), then a "Book this basket?" confirmation with the photo preview, the weight (e.g. "12.5 kg") with a Re-weigh button that discards the photo and starts over, and an optional note (`FormTextarea`, `value`/`input` bindings so Thai IME composition works) with Book and Discard. Success shows a transient notice for five seconds; failures show a tinted error notice (inside the confirmation for booking, at the top of the list otherwise). Actions are swipe gestures on `BaseSwipeCard` rows, shown only where the permission table allows them. Swiping right reveals a lime panel with the primary action: Load (the first waiting basket, operators), Unload (an In machine basket, operators) or Pick up (a Ready basket, its sender or an operator). Swiping left reveals a red Cancel panel on a basket the user may cancel (see the permission table), which opens the confirmation; for an In machine or Ready basket the confirmation says the basket is already in a machine or ready for pickup. Rows with no allowed action are not swipeable, and a swipe in an unavailable direction snaps back. Each swipeable row also carries visually hidden buttons for the same actions that Tab reaches and that appear while focused, because `BaseSwipeCard` has no keyboard path for its swipe panels. A row with a write in flight is disabled and shows an "Unloading…", "Picking up…" or "Updating…" veil with a spinner. Unload (operators only) runs the same weight prompt ("Weigh the washed basket") and camera, then uploads the photo with uploadWashQueuePhoto and sends one PATCH with the weight and photo URL; closing the prompt or camera saves nothing, and the row shows its own busy state during upload and save. Every row shows its before weight; Ready for pickup rows show "before → after kg". The photo viewer lists the booking photo and, for baskets that have one, the unload photo right after it. Each row has its own saving state; a 409 shows the server message and reloads the list. The weigh flow and the photo viewer are route-owned query overlays (`?weigh=book` or `?weigh=unload:<id>` opens the prompt, adding `&weight=<kg>` opens the camera; `?photo=<id>`) that close with Back. The page refreshes every 30 seconds while mounted (skipped while a write is in flight) and when the document becomes visible again, and disposes its timer on unmount. It is excluded from KeepAlive so booking state does not survive navigation away.

| Action | Who sees it |
|---|---|
| Book (Photo button) | Everyone |
| Cancel a Pending basket | The sender (`createdBy` equals the current StaffId), or an operator |
| Cancel an In Progress or Completed basket (stuck machine, test rows) | Admins only |
| Load (first Pending) and Unload | Operators only |
| Pick up (Completed) | The sender, or an operator |

Other people's baskets are view-only for non-operators.

Persistence uses the existing WashQueue tab, columns A through Q, in JOB_TICKETS_SPREADSHEET_ID. Capabilities are append and update; rows are never deleted. work_minutes is a nullable number reserved for future KPI use and is always written null on create; actions never change it. There is no duration calculation in this feature.
