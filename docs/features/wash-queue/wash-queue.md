# WashQueue

WashQueue is a shared washer and tumble-dryer basket queue for signed-in staff. Washers and dryers use the same booking form, statuses, actions and permissions. A sender photographs a basket and chooses structured wash options for a washer. Dryer bookings have no wash options. Legacy free-text instructions remain visible on older rows. It is independent of orders and JobTickets. Each `machine_id` has its own FIFO queue, ordered by createdAt ascending; the frontend groups baskets and shows the order, while the server only stores the selected machine id. FIFO is not enforced: any Pending basket can be loaded, in any order.

Every basket is weighed on the scale twice, and each weighing needs a photo of the basket on the scale as evidence. The sender enters the dry basket weight (`weightBeforeKg`) when booking; the staff member unloading enters the washed (wet) weight (`weightAfterKg`) when unloading. A booking starts Pending (Waiting). Loading changes Pending to In Progress (In machine), unloading changes In Progress to Completed (Ready for pickup), and collection changes Completed to Collected. Cancellation changes Pending, In Progress or Completed to Cancelled; earlier action stamps are kept. Each action stamps its corresponding timestamp and StaffId, plus updatedAt and updatedBy. Created and updated audit timestamps are produced by the existing repository audit configuration; action timestamps use formatBangkokTimestamp. All business timestamps use yyyy-MM-dd HH:mm:ss in Asia/Bangkok.

GET /api/wash-queue returns every Pending, In Progress and Completed basket, plus Collected and Cancelled baskets updated today in Bangkok. The result is an unpaginated array sorted by createdAt ascending in the standard success envelope. GET /api/machines requires the same approved-staff authentication and returns only ACTIVE Machines in an unpaginated standard success envelope, sorted by type (WSH before DRY), sortOrder ascending (null last), then id. Other methods return 405. POST /api/wash-queue accepts machineId (required trimmed non-empty string), photoUrl (a non-empty string, the booking photo taken on the scale), weightBeforeKg (required number), tagCode (one letter A–Z) and washOptions (required key, an options object for a washer or null for a dryer). The optional legacy instruction key (string or null) remains accepted but is ignored; new bookings always store instruction null, and returns the created basket with HTTP 201. The server generates WQ- followed by generateShortId(), sets Pending and workMinutes null, and takes both audit actors from authenticated req.staff.staffId. Before writing, the server validates machineId against an ACTIVE row in Machines and stores it as machine_id; unknown, MAINTENANCE or RETIRED machines return 422 with no write. Client-supplied identity, status and audit fields are rejected.

PATCH /api/wash-queue/:id accepts an `action`: load, collect or cancel alone, or unload together with `weightAfterKg` (number) and `unloadPhotoUrl` (the photo taken on the scale). It returns the updated basket. PATCH rejects machineId; the booked machine cannot be changed. An unknown id returns 404; an action incompatible with the current status returns 409 and an explanatory message. The frontend displays that message and reloads the list. Reads normalize native Sheets/GViz datetime values to the canonical Bangkok format, and blank nullable write echoes to null.

Every signed-in staff member can book, load, unload, pick up and cancel any basket; there are no role, ownership or FIFO checks in the frontend or the server, by owner decision. Sender names come from the staff store. Cancellation asks for confirmation. Shared Sheets reads and writes do not provide atomic compare-and-set across operators, so the status check is a read-before-update check, not a transactional concurrency guarantee.

GET /api/wash-products uses the same approved-staff authentication as GET /api/machines. It returns every ACTIVE and INACTIVE product in an unpaginated standard success envelope, sorted by type, sortOrder ascending (null last), then id. The DTO contains id, type (DETERGENT, SOFTENER or BLEACH), name, status (ACTIVE or INACTIVE), sortOrder and note. Other methods return 405. Inactive products remain readable so older bookings resolve their names.

The washOptions object has preRinse (boolean), soakMinutes (integer 1–720 or null), extraWash (boolean), temperature (cold, 40 or 60), bleach, detergent and softener (product ids or null), and rinses (1, 2 or 3). Unknown fields are rejected. The booked Machines row determines the type: a washer requires non-null washOptions, otherwise 422 "Choose the wash options."; a dryer requires null, otherwise 422 "Dryer bookings have no wash options." Each selected product must be ACTIVE with the matching type, otherwise 422 "Choose an available product." Products are read only for non-null washOptions. The server stores the object as JSON text in wash_options. Reads parse it leniently: blank, missing, malformed JSON or a schema-invalid object becomes null without failing the list.

Rows also carry `weightBeforeKg`, `weightAfterKg`, `unloadPhotoUrl`, `machineId` and `tagCode`, each nullable on reads for legacy rows; new bookings require `machineId` and `tagCode` (one letter A–Z). The tag is a movable physical letter: on the basket while waiting, on the machine while loaded, back on the basket after unload, freed on pickup or cancel.

The page is one screen at `/wash-queue`, so every staff member sees the whole queue of the current mode. It uses `ListPageLayout` with `GenericTabs` as the filters strip: All, Waiting, In machine and Ready, each with a count. The page opens on Waiting. The active tab lives in the `?tab=` query (`all`, `in-machine` or `ready`; Waiting has no key) and changes with `router.replace`. A floating switch at the bottom of the screen chooses Washer or Dryer; the mode lives in the `?mode=` query (`dryer`; Washer has no key) and changes with `router.replace`, keeping the other query keys. A basket belongs to Dryer when its `machineId` starts with `DRY`; every other basket, including legacy rows with no machine, belongs to Washer. Tabs, counts, sections, and empty states reflect only the current mode. The switch (`WashQueueModeSwitch`) is a 300×60 dark-primary rounded-square track with a lime rounded-square knob over the active half; each half has an icon (`local_laundry_service`, `mode_heat`) and the label Washer or Dryer, and the inactive half is faded white. It floats centred above the safe-area inset with one soft shadow, and the list ends with a spacer that clears it. The page loads the machines list into the machines store (`src/data/machines`) and the products list into the wash-products store (`src/data/wash-products`) on mount. The products store loads once, exposes items/loading/error, provides activeOf(type) sorted by sortOrder for pickers, and nameOf(id) for every status with an id fallback. All shows the sections from top to bottom as In machine, Waiting and a collapsible Ready for pickup, each hidden when empty; a filtered tab shows only its section. When the view has no rows, the active tab's section (Waiting for All) still shows its header and Photo button with a one-line empty message, so Washer and Dryer look the same. Each section header has a lime left bar, the title and a tiny uppercase subtitle; there is no basket counter (the tabs carry the counts). The Photo button sits at the right end of the header row of the topmost visible section; `WashQueueSection` exposes it as the `action` slot, beside the Ready section's collapse button rather than inside it. There is no swipe hint line. Rows are white cards with a weight column (the dry weight, or the washed weight on Ready rows, with "kg" under it), a thin divider, the tag letter (dark primary square, lime letter) then the sender with a "You" badge on the user's own baskets and a "Next" badge on the first waiting basket of each machine, an uppercase status line showing the booked machine label (e.g. DRYER 8 KG; legacy rows without a machine show IN MACHINE, WAITING or READY FOR PICKUP instead), coloured by status, a meta line (booking time as `today HH:mm` otherwise the Bangkok date and time — In machine rows show the load time instead as `Started at HH:mm:ss`, prefixed with the date when not today — then the wash option labels (or the legacy note when washOptions is null); Ready rows start it with "Dry X kg") and a 56 px photo tile that opens the shared photo viewer. The tile carries a status dot (dashed Waiting, primary sync In machine, lime check Ready), and Ready rows also show a small tile for the unload photo. The machine label is built in English from the Machines list as the type word and capacity, for example DRYER 15 KG or WASHER 10 KG (the Machines `name` column is not displayed), and falls back to the raw machine id when the machine is not in the list or has no capacity. FIFO is per machine: the Next badge counts the waiting baskets of the same `machineId` within the current mode, and legacy rows with no machine form one group. Booking is the Photo button (the shared `StickerFab` at 48 px, in the header row of the topmost visible section, or above the loading/error placeholder): the shared `WeightPrompt` ("Weigh the basket", explaining the photo must show the basket on the scale), then the shared CameraOverlay, then upload via uploadToStorage(file, 'wash-queue'), then a "Book this basket?" confirmation with the photo preview, the weight (e.g. "12.5 kg") with a Re-weigh button that discards the photo and starts over, a required machine picker, a required tag picker (`WashQueueTagPicker`, one horizontally scrolling row of A–Z buttons sent as `tagCode`; one pool shared by washers and dryers, duplicates are not checked), and the plain wash options form for a washer with Book and Discard. The picker (`WashQueueMachinePicker`) is three equal rounded-square tiles for the ACTIVE machines of the current mode, each with the capacity large and the type word Washer or Dryer small; unselected tiles are white with an outline border and the selected tile is dark primary with white text. A "Required" hint shows while nothing is chosen, nothing is pre-selected, Book stays disabled until a machine and tag are chosen and a washer has non-null draft options, the choice resets when the draft is discarded or booked, and it is sent as `machineId`. Success shows a transient notice for five seconds, centred just above the mode switch; failures show a tinted error notice (inside the confirmation for booking, at the top of the list otherwise). Actions are swipe gestures on `BaseSwipeCard` rows, available on every row. Swiping right reveals a lime panel with the primary action: Load (any waiting basket), Unload (an In machine basket) or Pick up (a Ready basket). Swiping left reveals a red Cancel panel, which opens the confirmation; for an In machine or Ready basket the confirmation says the basket is already in a machine or ready for pickup. A swipe in an unavailable direction snaps back. Only one row stays swiped open: opening another row, or pressing anywhere outside the open row (a page-level capture `pointerdown` listener), snaps it back, while a press on the open row's own action panel still runs the action. In machine rows have a running timer: the whole card wears the Weight field frame from `WeightPrompt` (2px primary border, radius 11px 15px 12px 14px, 4px 4px hard shadow in primary darkened 30%), set on the list item so the swipe panels stay clipped inside it and the frame, shadow and tab are never cut off, and a dark primary tab on the top-left edge (the same tab tokens as the field's "Weight" label, including the -3° tilt, drawn above the card and any open swipe panel) shows a clock icon and the elapsed time since `loadedAt` as H:MM:SS with tabular digits (`role="timer"`, not focusable). `loadedAt` is a Bangkok `yyyy-MM-dd HH:mm:ss` string parsed as Asia/Bangkok through `sheetTimestampMs`; when it is null or unparsable the row keeps the frame without a tab. Once the elapsed time passes `RUNNING_LONG_SECONDS` (1:30:00, in `format-elapsed.ts`) the tab, frame and shadow switch to the warning colour, as the field's invalid state switches to red. One page-level ticker (`useNow`, one interval, paused while the document is hidden) drives every timer, and the In machine list uses a 24px gap so a tab clears the previous card's shadow. Each swipeable row also carries visually hidden buttons for the same actions that Tab reaches and that appear while focused, because `BaseSwipeCard` has no keyboard path for its swipe panels. A row with a write in flight is disabled and shows an "Unloading…", "Picking up…" or "Updating…" veil with a spinner. Unload runs the same weight prompt ("Weigh the washed basket") and camera, then uploads the photo with uploadWashQueuePhoto and sends one PATCH with the weight and photo URL; closing the prompt or camera saves nothing, and the row shows its own busy state during upload and save. Every row shows its before weight; Ready for pickup rows show "before → after kg". The photo viewer lists the booking photo and, for baskets that have one, the unload photo right after it. Each row has its own saving state; a 409 shows the server message and reloads the list. The weigh flow and the photo viewer are route-owned query overlays (`?weigh=book` or `?weigh=unload:<id>` opens the prompt, adding `&weight=<kg>` opens the camera; `?photo=<id>`) that close with Back. The page refreshes every 30 seconds while mounted (skipped while a write is in flight) and when the document becomes visible again, and disposes its timer on unmount. It is excluded from KeepAlive so booking state does not survive navigation away.

The booking draft starts with washOptions null. Selecting a washer initializes defaultWashOptions only when the draft is null, preserving edits when switching washers; selecting a dryer clears it. Discarding or successfully booking resets it to null. Defaults are preRinse false, soakMinutes null, extraWash false, temperature cold, bleach null, the first ACTIVE detergent by sortOrder (or null), softener null and rinses 2. The row meta labels appear in order: Pre-rinse, Soak N min, Extra wash, 40°C or 60°C, bleach name, detergent name, softener name, Rinse N. Default flags and cold temperature are omitted; rinse count always appears. Product names resolve through the page's products store and fall back to ids.

`WashQueueWashOptionsForm.vue` is the replaceable plug-in component. Its stable props are modelValue: WashOptions and detergents, softeners, bleaches: readonly WashProductDto[]. It emits update:modelValue with a full new WashOptions object and never mutates the prop. WashOptions is derived from washOptionsSchema in the feature's plain TypeScript wash-options.ts. The current template is an unstyled placeholder with labeled native checkboxes, selects and a number input for every field. WashQueueBookDialog receives washOptions: WashOptions | null and the three product lists, emits update:washOptions, and renders the plug-in below the tag picker only for non-null options. It has no instruction prop or note field. The dev booking preview supplies sample products and default options and saves nothing.

Every action (book, load, unload, pick up, cancel) is open to every signed-in staff member, on any basket.

Persistence uses the existing WashQueue tab, columns A through W (23 fields), ending in machine_id, tag_code and wash_options, in JOB_TICKETS_SPREADSHEET_ID. Capabilities are append and update; rows are never deleted. work_minutes is a nullable number reserved for future KPI use and is always written null on create; actions never change it. There is no duration calculation in this feature. The read-only WashProducts tab shares JOB_TICKETS_SPREADSHEET_ID, uses columns A through H (id, type, name, status, sort_order, note, created_at, updated_at), disables append/update/delete and has no audit stamping. The read-only Machines tab shares JOB_TICKETS_SPREADSHEET_ID, uses columns A through I, disables append/update/delete and has no audit stamping.
