# WashQueue

WashQueue is a shared washer and tumble-dryer basket queue for signed-in staff. Washers and dryers use the same booking form, statuses, actions and permissions. A sender photographs a basket and chooses structured wash options for a washer. Dryer bookings have no wash options. Legacy free-text instructions remain visible on older rows. It is independent of orders and JobTickets. Each `machine_id` has its own FIFO queue, ordered by createdAt ascending; the frontend groups baskets and shows the order, while the server only stores the selected machine id. FIFO is not enforced: any Pending basket can be loaded, in any order.

POST reads Machines first; once the machine rules pass, a washer booking reads WashProducts and (for a non-CUSTOM program) WashPrograms in parallel. After a booking, the new row is shown from the POST response at once while the list reloads in the background, and a just-created row is kept for up to 30 seconds if a lagging read does not contain it yet.

Every basket is weighed on the scale when booking, with a photo of the basket on the scale as evidence. The sender may enter the dry basket weight (`weightBeforeKg`); it is optional, and a booking without it stores null. Unload weighing and photography are temporarily off; unloading currently needs neither. A booking starts Pending (Waiting). Loading changes Pending to In Progress (In machine), unloading changes In Progress to Completed (Ready for pickup), and collection changes Completed to Collected. Cancellation changes Pending, In Progress or Completed to Cancelled; earlier action stamps are kept. Each action stamps its corresponding timestamp and StaffId, plus updatedAt and updatedBy. Created and updated audit timestamps are produced by the existing repository audit configuration; action timestamps use formatBangkokTimestamp. All business timestamps use yyyy-MM-dd HH:mm:ss in Asia/Bangkok.

GET /api/wash-queue returns every Pending, In Progress and Completed basket, plus Collected and Cancelled baskets updated today in Bangkok. The result is an unpaginated array sorted by createdAt ascending in the standard success envelope. GET /api/machines requires the same approved-staff authentication and returns every Machines row of every status (ACTIVE, MAINTENANCE, RETIRED) in an unpaginated standard success envelope, sorted by type (WSH before DRY), sortOrder ascending (null last), then id. Other methods return 405. POST /api/wash-queue accepts machineId (required trimmed non-empty string), photoUrl (a non-empty string, the booking photo taken on the scale), weightBeforeKg (required key, a number or null), tagCode (one uppercase letter and three digits, e.g. A001) and washOptions (required key, an options object for a washer or null for a dryer). The optional legacy instruction key (string or null) remains accepted but is ignored; new bookings always store instruction null, and returns the created basket with HTTP 201. The server generates WQ- followed by generateShortId(), sets Pending and workMinutes null, and takes both audit actors from authenticated req.staff.staffId. Before writing, the server validates machineId against an ACTIVE row in Machines and stores it as machine_id; unknown, MAINTENANCE or RETIRED machines return 422 with no write. Client-supplied identity, status and audit fields are rejected.

PATCH /api/wash-queue/:id accepts an `action`: load, collect or cancel alone, or unload with `weightAfterKg` (number) and `unloadPhotoUrl` (the photo taken on the scale) together or neither. Sending only one unload field returns 422 before any read or write. A bare unload writes only the status, action stamp and audit actor fields. It returns the updated basket. PATCH rejects machineId; the booked machine cannot be changed. An unknown id returns 404; an action incompatible with the current status returns 409 and an explanatory message. The frontend displays that message and reloads the list. Reads normalize native Sheets/GViz datetime values to the canonical Bangkok format, and blank nullable write echoes to null.

Every signed-in staff member can book, load, unload, pick up and cancel any basket; there are no role, ownership or FIFO checks in the frontend or the server, by owner decision. Sender names come from the staff store. Cancellation asks for confirmation. Shared Sheets reads and writes do not provide atomic compare-and-set across operators, so the status check is a read-before-update check, not a transactional concurrency guarantee.

GET /api/wash-products uses the same approved-staff authentication as GET /api/machines. It returns every ACTIVE and INACTIVE product in an unpaginated standard success envelope, sorted by type, sortOrder ascending (null last), then id. The DTO contains id, type (DETERGENT, SOFTENER or BLEACH), name, status (ACTIVE or INACTIVE), sortOrder and note. Other methods return 405. Inactive products remain readable so older bookings resolve their names.

The washOptions object is `{ program, steps }`. The program is an ACTIVE WashPrograms program id, or CUSTOM when the steps are edited. It has 1–20 ordered steps. Every step has a type (stain_removal, quick_wash, normal_wash, rinse or soak) and up to 10 unique, trimmed, non-empty product ids. Wash steps require temperature (cold, 40 or 60); soak requires duration (integer minutes 1–720 or overnight); stain_removal and rinse have neither. Stain removal is manual pre-treatment by hand (brushing or spot-treating) before garments go into the machine. Unknown fields are rejected at every level. A washer requires non-null options, otherwise 422 "Choose the wash program."; a dryer requires null, otherwise 422 "Dryer bookings have no wash options." Every product in every step must exist and be ACTIVE, regardless of product type, otherwise 422 "<name> (<id>) is not an available product. Remove it from the step." (just the id when the product is unknown) A non-CUSTOM program must exist and be ACTIVE, otherwise 422 "Choose an available program." WashPrograms is only read for non-CUSTOM options; dryers read neither master. The server stores JSON text in wash_options. Blank, missing, malformed JSON or schema-invalid stored options become null without failing the list; legacy instruction remains the fallback.

GET /api/wash-programs uses the same approved-staff authentication as wash-products. It returns every ACTIVE and INACTIVE program as `{ id, name, status, sortOrder, steps }`, grouped by program_id. Name, status and sortOrder come from the first sheet row; steps sort by step_no. Products split on commas, trim and drop blanks. Blank wash temperature defaults to cold, and numeric soak duration becomes integer minutes; overnight is case-insensitive. Temperature and duration cells are ignored for stain_removal, which returns only type and products. Invalid step rows are skipped and programs with no valid steps are dropped. Programs sort by sortOrder ascending (null last), then id. Other methods return 405. The route is loaded lazily. Inactive programs remain available to resolve historical booking names.

Rows also carry `weightBeforeKg`, `weightAfterKg`, `unloadPhotoUrl`, `machineId` and `tagCode`, each nullable on reads for legacy rows; new bookings require `machineId` and `tagCode` (one uppercase letter and three digits, e.g. A001); the server checks only that format, never uniqueness. The booking sheet fills the tag itself: each machine gets a letter from its position among Machines of the same type, every status included, ordered by sortOrder (null last) then id — washers A–M, dryers N–Z, with no O (it reads as zero); a machine past the 13th washer or 12th dryer has no letter and its tag starts empty. The number is one more than the highest number already used today (Bangkok, by createdAt) by that letter in the loaded queue, from 001; at 999 the tag starts empty. Letters are derived at runtime from the Machines sheet, so reordering or adding machines there moves them. GET /api/machines is cached for 24 hours and persisted in localStorage; the sidebar refresh control clears it. The physical tag is handwritten with the booked tag code: on the basket while waiting, on the machine while loaded, back on the basket after unload, freed on pickup or cancel.

The page is one screen at `/wash-queue`, so every staff member sees the whole queue of the current mode. It uses `ListPageLayout` with `GenericTabs` as the filters strip: All, Waiting, In machine and Ready, each with a count. The page opens on Waiting. The active tab lives in the `?tab=` query (`all`, `in-machine` or `ready`; Waiting has no key) and changes with `router.replace`. A floating switch at the bottom of the screen chooses Washer or Dryer; the mode lives in the `?mode=` query (`dryer`; Washer has no key) and changes with `router.replace`, keeping the other query keys. A basket belongs to Dryer when its `machineId` starts with `DRY`; every other basket, including legacy rows with no machine, belongs to Washer. Tabs, counts, sections, and empty states reflect only the current mode. The switch (`WashQueueModeSwitch`) is a 300×60 dark-primary rounded-square track with a lime rounded-square knob over the active half; each half has an icon (`local_laundry_service`, `mode_heat`) and the label Washer or Dryer, and the inactive half is faded white. It floats centred above the safe-area inset with one soft shadow, and the list ends with a spacer that clears it. The page loads the machines list into the machines store (`src/data/machines`) and the products and programs lists into their wash-products and wash-programs stores on mount. The products store loads once, exposes items/loading/error, provides activeOf(type) sorted by sortOrder for pickers, and nameOf(id) for every status with an id fallback. All shows the sections from top to bottom as In machine, Waiting and a collapsible Ready for pickup, each hidden when empty; a filtered tab shows only its section. When the view has no rows, the active tab's section (Waiting for All) still shows its header and Photo button with a one-line empty message, so Washer and Dryer look the same. Each section header has a lime left bar, the title and a tiny uppercase subtitle; there is no basket counter (the tabs carry the counts). The Photo button sits at the right end of the header row of the topmost visible section; `WashQueueSection` exposes it as the `action` slot, beside the Ready section's collapse button rather than inside it. There is no swipe hint line. Rows are white cards with a large tag letter in the left column (a muted “–” when no tag is recorded), the smaller weight underneath as “<figure> kg”, a thin divider, then the sender with a "You" badge on the user's own baskets and a "Next" badge on the first waiting basket of each machine, an uppercase status line showing the booked machine label (e.g. DRYER 8 KG; legacy rows without a machine show IN MACHINE, WAITING or READY FOR PICKUP instead), coloured by status, a meta line (booking time as `today HH:mm` otherwise the Bangkok date and time — In machine rows show the load time instead as `Started at HH:mm:ss`, prefixed with the date when not today — then the wash program summary (or the legacy note when washOptions is null); Ready rows start it with "Dry X kg") and a 56 px photo tile that opens the shared photo viewer. The tile carries a status dot (dashed Waiting, primary sync In machine, lime check Ready), and Ready rows also show a small tile for the unload photo. The machine label is built in English from the Machines list as the type word and capacity, for example DRYER 15 KG or WASHER 10 KG (the Machines `name` column is not displayed), and falls back to the raw machine id when the machine is not in the list or has no capacity. FIFO is per machine: the Next badge counts the waiting baskets of the same `machineId` within the current mode, and legacy rows with no machine form one group. Booking is the Photo button (the shared `StickerFab` at 48 px, in the header row of the topmost visible section, or above the loading/error placeholder). It opens the "Book this basket?" sheet directly, with the description "Put the basket on the scale, enter its weight and take a photo that shows it on the scale." The sheet holds, from top to bottom: the photo preview (the shared `PhotoCapturePanel`, passive here: only the Photo sticker takes the photo), the weight field with the Photo sticker, then the wash program section (washer) or the machine tiles (dryer), and Discard / Book. Before a photo the preview is a 200 px dashed frame (2px dashed primary mixed 40% with white, no fill) with the bag-scan empty state: a lime-tint rounded camera tile tilted -7°, "No photo yet" and "Weigh the basket, then tap Photo." After the photo it is a square (1:1) image. The weight field is the shared `WeightField` (the same field `WeightPrompt` uses) with 18px above and below; its Photo sticker stays disabled only while a typed weight is invalid (an empty field is fine), opens the camera as the route-owned `?shoot=book` overlay, and uploads with uploadWashQueuePhoto; once a photo exists the sticker turns dark primary with a lime icon and reads Retake. The tag is a white sticker label (kg-badge style, tilted -4°) on the photo's top-left (`WashQueueTagLabel`) showing "TAG" over an editable field that holds the automatic tag, or an orange "?" placeholder when it is empty. Staff may type over it (uppercased, up to four characters); once they do, it no longer follows machine changes or queue reloads until the draft resets. Opening the sheet reloads the queue, selects the first ACTIVE machine of the mode (lowest sortOrder) when none is chosen, and fills the tag for that machine. In washer mode the washer is chosen from an icon button at the right of the Wash program header (`WashQueueMachineMenu`, white with a primary edge and icon like the kg badge, dark primary with a lime icon while open, with a wiggle and lime ring every 2.4 s while no washer is chosen); its dropdown lists the ACTIVE washers as "Washer N kg" with the selected one lime and checked. Dryer mode keeps the three capacity tiles (`WashQueueMachinePicker`). Book stays disabled until a photo, a machine of the current mode and a tag in the A001 format are set, and while a typed weight is invalid (and, for a washer, options with at least one step); the draft resets when discarded or booked, and the machine is sent as `machineId`. There is no success notice; load, unload, pick up and cancel show the row's busy veil ("Updating…", "Unloading…", "Picking up…") for at most 1.2 s (ROW_MOVE_HOLD_MS); the row then moves optimistically while the save finishes in the background, or earlier with the server row if the save returns first. A just-confirmed row is kept over an older GViz read until the list catches up. Booking failures show a tinted error notice inside the booking sheet. A failed row action reloads the list from the server, undoing the optimistic move, and shows the error on that row's card, in the place of the busy veil (red text and an error icon on a white veil, not interactive), for six seconds or until the next action on that row; when the row is no longer listed the error falls back to the notice at the top of the list. Actions are swipe gestures on `BaseSwipeCard` rows, available on every row. Waiting and In machine baskets share the same right-swipe action: swiping right loads or unloads immediately, without a panel tap. For Ready baskets, swiping right reveals a lime Pick up panel, which requires a tap. Swiping left reveals a red Cancel panel, which opens the confirmation; for an In machine or Ready basket the confirmation says the basket is already in a machine or ready for pickup. A swipe in an unavailable direction snaps back. Only one row stays swiped open: opening another row, or pressing anywhere outside the open row (a page-level capture `pointerdown` listener), snaps it back, while a press on the open row's own action panel still runs the action. In machine rows have a running timer: the whole card wears the Weight field frame from `WeightPrompt` (2px primary border, radius 11px 15px 12px 14px, 4px 4px hard shadow in primary darkened 30%), set on the list item so the swipe panels stay clipped inside it and the frame, shadow and tab are never cut off, and a dark primary tab on the top-left edge (the same tab tokens as the field's "Weight" label, including the -3° tilt, drawn above the card and any open swipe panel) shows a clock icon and the elapsed time since `loadedAt` as H:MM:SS with tabular digits (`role="timer"`, not focusable). `loadedAt` is a Bangkok `yyyy-MM-dd HH:mm:ss` string parsed as Asia/Bangkok through `sheetTimestampMs`; when it is null or unparsable the row keeps the frame without a tab. Once the elapsed time passes `RUNNING_LONG_SECONDS` (1:30:00, in `format-elapsed.ts`) the tab, frame and shadow switch to the warning colour, as the field's invalid state switches to red. One page-level ticker (`useNow`, one interval, paused while the document is hidden) drives every timer, and the In machine list uses a 24px gap so a tab clears the previous card's shadow. Each swipeable row also carries visually hidden buttons for the same actions that Tab reaches and that appear while focused, because `BaseSwipeCard` has no keyboard path for its swipe panels. The weigh+photo unload flow keeps its busy veil for the whole upload and save; for the other actions a second action on the same row is ignored while one is in flight. Unload currently sends a bare PATCH with no prompt or camera. The retained weigh flow, when restored, runs the weight prompt ("Weigh the washed basket") and camera, uploads the photo with uploadWashQueuePhoto and sends one PATCH with the weight and photo URL; closing the prompt or camera saves nothing, and the row shows its own busy state during upload and save. Ready for pickup rows use the washed weight when recorded, otherwise the dry weight; other rows use the dry weight. There is no tag square before the sender name. The photo viewer lists the booking photo and, for baskets that have one, the unload photo right after it. A 409 reloads the list from the server, undoing the optimistic move, and shows the server message on the card. The booking camera and photo viewer are route-owned query overlays (`?shoot=book` opens the booking camera over the sheet; `?photo=<id>` opens the viewer) that close with Back. The retained unload weigh flow uses `?weigh=unload:<id>` for the prompt and adds `&weight=<kg>` for the camera, but unload actions do not open it while weighing is temporarily off. The page refreshes every 30 seconds while mounted (skipped while a write is in flight) and when the document becomes visible again, and disposes its timer on unmount. It is excluded from KeepAlive so booking state does not survive navigation away.

Tapping a closed card opens a route-owned bottom detail sheet at ?basket=<id>; tapping a swiped-open card closes its swipe panel. The detail looks up the basket in the current store items and renders nothing for a missing id. Its header shows the big tag (or “–”), sender, machine label and status. It shows one large square photo, the booking photo first; when an unload photo exists it is a second slide, with two dots centred at the bottom (white for the current one, tappable). Staff change slides by swiping on touch, dragging with the mouse (a drag does not open the viewer), the mouse wheel over the photo (at the first or last slide the wheel scrolls the sheet instead) or the dots; tapping a photo opens the shared photo viewer on it. Then the before and after weights, machine, sender, and booked, loaded and unloaded times, with “–” for missing weights and times. Below these are the recorded program name and every step in the booking form’s read-only summary style, or a “No program recorded” box, followed by the legacy instruction note only when non-empty. Photo taps on either the row or detail open only the existing viewer at ?photo=<id> or ?photo=<id>:after. The detail hides while the photo viewer is open so its frame and focus trap cannot cover or intercept the viewer; closing the viewer returns to the detail. X, the backdrop and browser or Android Back close the detail; on a fresh deep link, X and the backdrop remove only the basket query.

The booking draft starts with washOptions null. Opening the sheet in washer mode sets defaultWashOptions (a deep copy of the first ACTIVE program, or one cold normal_wash step with no products and program CUSTOM when none are available), and fills it when the programs list arrives later; dryer bookings send null. Discarding or successfully booking resets it to null. The programs store loads once, exposes items/loading/error, active() sorted by sortOrder (null last) then id, and nameOf(id) for historical summaries (Custom when missing). Row meta uses washOptionsSummary: program name or Custom, step count and soak summary.

The wash program section is read-only: steps are edited in the WashPrograms sheet, not in the app. Program stickers show the name and step count, with a dark-primary selected sticker and lime check badge; tapping one replaces the options with a deep copy of its steps. Below them the framed Program summary (tilted "Program" tab) shows "<program> · N steps" with the chosen washer ("Washer 15 kg") at the right end, then, under a dashed divider, a vertical progress line of the steps: a 2px outline-variant line with 10px primary dots (the last one lime), each step name in 800 15px headline and its detail in 600 13px body on-surface-variant — temperature or duration, then product names, joined by "·" ("Water only", "By hand" or "No product" when there is none). There is no step editing, reordering, Add step or Custom pill. `WashQueueWashOptionsForm.vue` takes modelValue: WashOptions, programs (ACTIVE only), productName(id) and machine (label or null), has an `action` slot in the header for the washer menu, and emits update:modelValue with a complete new object. The unauthenticated dev preview at /#/dev/wash-queue-book uses representative machines and programs, starts with no photo, and saves nothing.

## Unload weighing temporarily off (2026-10-12)

The owner turned unload weighing and photography off temporarily and will bring them back. Swiping right on an In machine row unloads at once with no prompt, camera or panel tap. PATCH unload accepts weightAfterKg and unloadPhotoUrl together or neither; one alone returns 422. Rows unloaded without them have null weightAfterKg and unloadPhotoUrl and show the before weight. Booking is unchanged.

To restore unload weighing, set UNLOAD_WEIGH_REQUIRED to true in src/features/wash-queue/unload-policy.ts and make both fields required again in the contract.

Every action (book, load, unload, pick up, cancel) is open to every signed-in staff member, on any basket.

Persistence uses the existing WashQueue tab, columns A through W (23 fields), ending in machine_id, tag_code and wash_options, in JOB_TICKETS_SPREADSHEET_ID. Capabilities are append and update; rows are never deleted. work_minutes is a nullable number reserved for future KPI use and is always written null on create; actions never change it. There is no duration calculation in this feature. The read-only WashProducts tab shares JOB_TICKETS_SPREADSHEET_ID, uses columns A through H (id, type, name, status, sort_order, note, created_at, updated_at), disables append/update/delete and has no audit stamping. The read-only Machines tab shares JOB_TICKETS_SPREADSHEET_ID, uses columns A through I, disables append/update/delete and has no audit stamping.

The read-only WashPrograms tab shares JOB_TICKETS_SPREADSHEET_ID, uses columns A through L in this order: id, program_id, program_name, step_no, step_type, products, temperature, duration, status, sort_order, created_at, updated_at. Append, update and delete are disabled, with no audit stamping. There is no data migration because the program model replaces the undeployed flat options.
