# Order item — API contract

Module `order-items` (Phase 1). Source: [`docs/plans/orders-backend.md`](../../../plans/orders-backend.md).
Sheet: `OrderItemForms` (read + append).

## `GET /api/order-items` — list

Query
- `orderId` — string, **required** → missing is 422 (a bare list would return the whole 23,165-row sheet)
- `keyword` — string, default `''` (no-op)
- `page` — int > 0, default 1
- `perPage` — int > 0, max 500, default 500
- `sortBy` — `createdAt`, default `createdAt`
- `sortOrder` — `asc` | `desc`, default `asc`

Response `200 { data: OrderItemResponse[], meta.pagination: { page, perPage } }`
- `orderItemId` — string
- `orderId` — string | null
- `itemId` — string | null
- `description` — string | null
- `quantity` — number | null
- `price` — number | null
- `creditsUsed` — number | null
- `category` — string | null (free string on read)
- `serviceType` — string | null (server-derived, never client-supplied; free string on read, Thai legacy values returned verbatim)
- `specialInstructions` — string | null
- `createdAt` — string | null
- `createdBy` — string | null

Notes
- rows with a blank `orderItemId` (the 1,074 live phantom rows) are dropped by the service
- `invoiceItemId` is not exposed
- dirty values are never coerced or normalised
- readable but not client-writable, because another process owns each one:
  - `creditsUsed` — package-credit consumption (out of scope of the orders plan)
  - `invoiceItemId` — written by invoicing at invoice time; blank on every live row today
  - `serviceType` — derived from the parent order on create

## `GET /api/order-items/:id` — detail

Path
- `id` — `OrderItemForms.id`

Response `200 { data: OrderItemResponse }` — same fields as list.

Errors: 400 blank id · 404 not found · 409 multiple rows.

## `POST /api/order-items` — create

Request
- `orderId` — string, required
- `itemId` — string, optional, nullable, default `null` (link to the `OrderItems` catalogue row)
- `description` — string, nullable, default `null`
- `quantity` — number > 0, required
- `price` — number ≥ 0, nullable, default `null`
- `category` — enum `Tops` | `Bottoms` | `Home Textile` | `Others`, nullable, default `null`
- `specialInstructions` — string, nullable, default `null`
- `createdBy` — string, required
- not accepted: `orderItemId`, `serviceType`, `creditsUsed`, `invoiceItemId`, `updatedAt`, `updatedBy`, `timestamp`

Response `201 { data: OrderItemResponse }` — same fields as list.

Behaviour
- `orderItemId` is server-generated by `generateShortId()` (`server/shared/utils/id.ts`) — an
  8-character lowercase hex id with **no prefix**, matching the live `OrderItemForms.id` column
- `serviceType` is filled by the service layer from the parent order's `OrderForm.service_type`;
  the client cannot set it, and one order carries exactly one service type
- an `orderId` that resolves to no `OrderForm` row → 404; the lookup doubles as `orderId` validation
- `createdAt` is stamped by `audit.onAppend`
- `Bedding` is not an accepted category (1 legacy row only) → 422
- a duplicate generated id surfaces as 500 (`DuplicatePrimaryKeyError`)

## Not available

- `PATCH` / `DELETE` — 405; `writes.update` and `writes.delete` are `false`

## Notes on `createdAt`

Kept in the response and pinned by the dry-test. `sortBy=createdAt` sorts at the GViz query layer,
not in the projection, so removing it later would be a contract plus dry-test change — not a free
decision.
